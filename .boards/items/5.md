The piece that turns the chooser (item 4) plus the admin (item 3) into something worth
selling: the owner edits the page **on the page**, reorders blocks by dragging, and sees
the result as they work rather than after a publish.

Depends on item 3 phases 0–2 (content in Postgres behind a REST API, and a block editor
that can express the schema) and on item 4 (the axes it previews).

## Why this is the differentiator, not a nice-to-have

Item 3 phase 0 alone removes the redeploy complaint, which is the *stated* frustration.
This is the thing that makes the product better than what customers already have rather
than merely less annoying. Both existing customer sites are block-composed already, so
reordering is the single most common edit either owner makes.

## What already exists

- **Block ordering is already positional.** In `content/pages/*.json` the `blocks[]`
  array's index *is* the order — no explicit order field, no ids. Drag-reorder is an
  array splice, and the persistence side is genuinely trivial.
- **`imageSide: 'auto'` already recomputes on drag-reorder** in Tina today, alternating
  image sides left/right by position. That behaviour has to survive; any new reorder UI
  must trigger the same recompute or images will stop alternating.
- **The preview mechanism is nearly ready** — see item 4's "Preview is nearly free",
  including the two fixes needed (sessionStorage iframe collision; `initPreview` reading
  `location.search` only once).

## What has to be built

- **Drag-and-drop reordering** of `blocks[]`, with a keyboard-accessible equivalent —
  a reorder control that only works by mouse fails the owner on a tablet, which is where
  at least one of these owners actually works.
- **Inline editing over the real DOM.** `contentEditable` on text fields plus block-level
  selection. Note the lesson already learned on the `/keeper` edit demo: keep the fields
  **uncontrolled** — text children as constant strings so React never writes to the node
  after mount — or the caret fights every keystroke.
- **Live preview of the three axes** while editing, without writing to the store, which
  is exactly what `preview.js` already does non-destructively for style and season.
- **Optimistic save with conflict handling.** No existing repo has this; the marketplace
  re-fetches everything after each mutation and SSS's admin does the same.

## Traps carried over from the existing sites

- **Reveal animations must never animate `opacity`.** LSS animates `translate` only,
  inside a `@supports (animation-timeline: view())` + `prefers-reduced-motion:
  no-preference` guard. A `fill: both` animation starting at `opacity: 0` renders its
  before-phase whenever its clock has not advanced, and a page in a background tab has a
  frozen document timeline — which blanked the entire site on 2026-07-22. An editor that
  renders the site in a hidden or detached iframe hits exactly that condition.
- **Same trap, this repo's version:** `useScrollReveal`'s `.reveal-ready` gate hides
  every `[data-reveal]` section until its observer is armed, and a backgrounded tab
  delivers no IntersectionObserver callbacks at all. Anything that mounts the site
  off-screen has to handle both.
- **Cross-references are free text validated on save.** `buttons[].service` and
  `bookingOptions[].addOns[].service` resolve case-insensitively against `service`-block
  titles *on the same page*. Reordering or renaming a service block can break a button
  silently — the editor should surface that, since Tina's save-time validation would no
  longer be there to catch it.

Customers are giving consistent frustrated feedback about TinaCMS. The core of it is
structural, not cosmetic: Tina is **git-backed, so every content edit is a commit and a
redeploy**, and the live SPA additionally queries TinaCloud at runtime with a documented
per-branch indexing footgun (a stale `TINA_BRANCH` in Vercel silently defeated a fix on
2026-07-23; a deploy whose origin is not registered in TinaCloud renders "Page not
found" on every page despite a green build).

**Decision taken:** this becomes a **new repo**, its own product, with Live Spirit Seeds
as the first customer and migration target. Not built inside LSS — it would grow roots
in one client's site and extracting it later is the expensive version of this decision.

## The estimate

**The rendering half is nearly free. The authoring UX is the entire project.**

Only three files under LSS `src/` import anything Tina: `pages/DynamicPage.jsx`
(`useTina`, the generated client), `components/cms/Blocks.jsx` (`tinaField` at ~14 sites,
`TinaMarkdown` once, and a `__typename` switch that would become `_template`), and
`cms/site.js` (two queries). Swapping those to REST is **~40 lines**. Nothing in layout,
styling, block dispatch, button/add-on resolution, or the preview system changes.

| Phase | Work | Est. |
| --- | --- | --- |
| 0 | Content out of git into Postgres + REST; the ~40-line render swap. **Kills the redeploy pain.** | 1–2 wk |
| 1 | Auth + admin shell — lift `lib/auth.ts`, `lib/supabase/*`, `requireOwner()` and the RLS write-isolation from `LiveSpiritSeedsMk2/marketplace`; its README says the folder is self-contained | 1 wk |
| 2 | **The block editor** — schema-driven forms, repeating object lists, `defaultItem` presets, cross-reference validation, drag-reorder | **4–6 wk** |
| 3 | Inline editing + live preview | 3–4 wk |
| 4 | Media library (upload + cursor-position markdown insert are drop-in from the marketplace; browse/reuse/delete are not) | 1 wk |
| 5 | Revision history | 1–2 wk |

**Minimum that kills the complaint: 0 + 1 + a cut-down 2 ≈ 6–8 weeks. A product that
genuinely beats Tina for these customers: 3–4 months.**

## Four things that make or break the number

- **Phase 2 is the whole project.** The marketplace's `ProductForm.tsx` is a flat,
  fixed-field form. Tina's `tina/config.ts` is a 555-line *block-based page builder*
  with repeating lists, `ui.itemProps` labels, and typed cross-references (the
  `buttons[].service` → service-block-title resolver). That delta is the estimate.
- **Leaving git costs revision history**, which Tina gave away free. Phase 5, and easy
  to forget until a customer overwrites a page.
- **Neither existing repo has migration tooling.** SSS uses inline
  `CREATE TABLE IF NOT EXISTS`; the marketplace uses a hand-maintained `schema.sql` with
  `add column if not exists`. `IF NOT EXISTS` silently no-ops once the table exists, so
  an evolving content model breaks quietly. **Solve this in phase 0.**
- **"Owner" in the marketplace means any authenticated Supabase user** — no role column,
  no allowlist; security rests on the operator disabling public sign-ups. Single-owner
  is a week; multi-editor needs a roles model that exists nowhere. Also: the marketplace
  has no `middleware.ts` despite a comment claiming session refresh happens there.

## What is genuinely reusable

From `LiveSpiritSeedsMk2/marketplace` — close to copy-paste: Supabase auth, the 13-line
`requireOwner()` gate applied at both page and server-action level, RLS with deliberately
zero write policies, image upload to Supabase Storage with UUID keys, **inline image
insertion at the textarea cursor position**, categories + `text[]` tags with URL-synced
filters, Postgres FTS over a generated `tsvector`, `slugify()` + collision loop,
draft/active publish gating, and a per-record theme/ui_style override — a working
precedent for "brandable".

From `storyShapedStudios` — a clean REST idiom, the `apiFetch` helper, the field-allowlist
PATCH pattern, the `hasDb` graceful-degradation convention, and one competent
`BEGIN`/`SELECT … FOR UPDATE`/`COMMIT` transaction. **No auth exists anywhere in that
repo** — confirmed, not merely undocumented.

## Exists in neither repo

Block/repeating-field editor · content-model definition layer · WYSIWYG or live preview ·
media *library* (upload-only today) · revision history · roles/invites/multi-editor ·
migration tooling · any tests.
